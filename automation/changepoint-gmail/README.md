# 変化点承認依頼メールの設定

送信元は `miyama.firebase@gmail.com`。作成・再編集後は発信部署、対応スタンプ押印後は発生部署のマスターに登録された承認者へ、5分間隔の定期処理で通知します。コードを配置するだけでは送信は始まりません。初回認証と以下の設定が必要です。

生産予定日の入力・変更、および発生部署の最終承認完了は、作成部署（発信部署）の「通知先」へ送ります。この通知先は承認依頼先とは別に設定します。対応者スタンプだけでは作成部署へ通知しません。通知先が未設定の場合、承認者への代替送信はせず保留します。

登録時の展開メールは、部署マスターの「展開先」に登録した複数アドレスへ送ります。登録画面で展開先部署を複数選択できます。発信部署と変化点発生部署は必須で、外せません。同一部署や同一アドレスは重複送信しません。承認先・通知先とは別設定で、未設定の場合に代替送信はしません。

作成済みのApps Script: [変化点管理 承認依頼メール](https://script.google.com/home/projects/1xhyIESQPR9bA9rbgUjgthWRtTQQwVx5R2bROQa34yU_Jcj3XKh5No9Db/edit)。2026年10月8日13:10（日本時間）から自動配信が稼働中です。同日、利用者の承認を受けて登録済み9部署・29アドレスへ送信許可を拡大し、14:30に社内マスター宛先の自動許可も有効化しました。初回認証とFirestore読み取りは確認済みですが、受信者側への到着は未確認です。更新時にトリガーや開始日時を初期化しないでください。

登録完了後は「変化点カードを印刷して現場リーダーへ渡してください」と案内します。「印刷する」で新規登録したカードの原本・コピーの印刷画面を開きます。「後で」を選択した場合も登録結果の印刷ボタンから再度開けます。印刷の失敗やキャンセルで登録をやり直す必要はありません。

メールのリンク見出しは「変化点情報リンク」とし、メール本文には印刷・現場リーダーへの手渡し案内を載せません。生産予定日が未定の未完了案件では、発生部署の現場管理者に次回生産予定日の入力を促す文と、`productionDateId` を使った直接入力リンクを展開メール・承認依頼に追加します。既送信メールは変更・再送しません。従来のチェック・承認リンクから開いた画面にも、予定日未定時の入力リンクを表示します。登録直後のアプリ内印刷案内は従来どおりです。

対応者の押印には、チェック完了に加えて「実際の切替日」「実際の切替時刻（日本時間、分単位）」が必要です。`actualSwitchDate` / `actualSwitchTime` を対応スタンプと同時保存し、予定日 `occurrenceDate` は上書きしません。最終承認待ちの既存案件には遡及して入力を強制せず、記録のない過去案件は「未記録」と表示します。

期限超過の状況確認メールは2026年10月8日に有効化しました。初回は10月9日（金）9時以降、その後は平日（月〜金）の9時以降です。部署マスターに登録した社内宛先を自動許可します。未設定・不正・未許可の社外宛先を含む通知は送信せず保留します。Firestoreでの対象抽出は確認済みで、日次メールの実配送は開始後に確認します。

## 部署マスターの宛先を自動許可

- `AUTO_ALLOW_MASTER_RECIPIENTS=true` の場合、送信時に最新の部署マスターから解決した承認先・通知先・展開先のうち、ドメインが `miyama-unitec.co.jp` と完全一致するアドレスを自動許可します。新規追加時にApps Scriptの許可リストを編集する必要はありません。通常は次回の5分間隔の処理で反映されます。
- 社外アドレス、サブドメイン、似たドメインは自動許可しません。社外送信が必要な場合は個別承認後に `ALLOWED_RECIPIENTS` へ追加します。いずれか1宛先でも不正・未許可なら通知全体を保留し、許可済みの一部だけには送りません。
- 削除・変更した宛先は最新のマスターに基づいて判定します。自動許可分を固定の許可リストへ蓄積する処理は行いません。宛先未設定時の他の役割への代替送信も行いません。
- 有効化は専用Gmail所有者が `enableAutomaticMasterRecipients` を実行します。無効化する場合は上記プロパティを `false` にすると固定許可リストだけの判定に戻ります。トリガー、通知開始日時、取得位置、送信記録は変更しません。
- マスターを変更できる利用者は社内送信先も変更できるため、担当者・変更手順・アクセス管理を社内で定めてください。自動許可は本人確認やマスター編集権限を新設する機能ではありません。
- 2026年10月8日の切替時に保留していた承認依頼・展開通知の2件は、再判定で対象外となり `skipped` で終了しました。再送・過去案件の一斉送信はしていません。

## 初回設定

1. 会社で管理する上記Googleアカウントで https://script.google.com/ にログインし、スタンドアロンのApps Scriptプロジェクトを作成します。
2. 同梱の `Code.gs` と `appsscript.json` を設定します。マニフェストはプロジェクトの設定から表示できます。ウェブアプリとして公開する必要はありません。
3. Firebase管理者が、プロジェクト `abnreport-fd733` のGoogle Cloud IAMで送信元アカウントに `Cloud Datastore Viewer` (`roles/datastore.viewer`) を付与します。これはデータベース全体の読み取り権限です。管理者が許可範囲を確認してください。メール処理はFirestoreへの書き込みを行いません。既存のFirestoreルールは変更しません。
4. アプリの「マスター管理 → 部署 → 承認先」で、各部署の承認者名・メールアドレスを登録します。同じ行の「通知先」で、生産日・承認完了の結果を受け取る部署のメールアドレスを登録します。どちらもカンマ区切りで複数登録でき、セミコロン・空白・改行・全角区切りにも対応します。重複は除外します。1設定につき50件、合計6000文字までです。既存の1件設定や部署の配布リストも使用できます。
5. 「展開先」もカンマ区切りで複数登録できます。社内宛先の自動許可を使う場合は、管理者の承認後に `enableAutomaticMasterRecipients` を実行します。固定許可方式の場合はスクリプトプロパティ `ALLOWED_RECIPIENTS` に、送信を許可する全メールアドレスをカンマ区切りで設定します。未許可の社外アドレスには送信しません。
6. `previewNotifierConfiguration` を手動実行してGoogleの認証を行い、実行ログで送信元・宛先とFirestore読み取りを確認します。認証エラーが出た場合、アプリの公開ルールを緩めず、IAMとスコープを確認してください。
7. 確認後、`startApprovalNotifications` を一度実行します。以後、パソコンやOutlookを起動しておく必要はありません。
8. 開始後にテストカードを作成して受信確認し、発信部署承認、対応チェック、対応スタンプの順に進め、発生部署承認者にも届くことを確認してください。実際の宛先へ通知されるため、テスト相手に事前連絡してください。

設定前のカードを一斉送信しないため、初回開始日時より前の依頼は対象外です。旧版アプリで作成された依頼にも通知日時がないため、対象外です。全利用者が最新版を再読み込みしてから開始してください。開始時刻はサーバーの実行時刻で記録します。

## 運用

- 予定日超過の状況確認は、`enableDailyOverdueReminders` で有効化します。既存の5分間隔トリガーを利用し、初回設定の翌日から日本時間9時以降に、案件ごとに1日1回送ります。9時ちょうどの配信は保証せず、処理量・残枠・宛先設定で遅れる場合があります。`disableDailyOverdueReminders` は状況確認だけを停止し、他の通知は継続します。
- 状況確認の宛先は現在の状態で決まります。発信部署の承認待ち → 発信部署の「承認先」、発生部署の対応待ち → 発生部署の「展開先」、発生部署の最終承認待ち → 発生部署の「承認先」です。個人の氏名からメールを推測せず、登録された部署別宛先を使います。本文に予定日・現在の状態と、直接チェック・承認画面を開くリンクを載せます。
- 状況確認は有効な予定日が昨日以前の未完了ワークフローを対象にします。予定日未定・当日・未来、中止・完了・削除済み、ワークフロー状態が未設定の旧データは除外します。有効化前に登録された案件でも、明示的な承認状態があり期限を超過していれば対象です。メールを読むだけで承認されることはありません。
- 状況確認は平日（月〜金）のみが初期設定です（祝日の自動判定はしません）。`REMINDER_WEEKDAYS_ONLY` を `false` にすると土日も含む毎日になります。`REMINDERS_START_DAY` は初回開始時に自動設定され、既存の通知開始日時や取得位置を変更しません。
- 状況確認は送信直前に状態・予定日を再確認します。承認が進んでいれば現在の担当先に切り替え、完了済み・予定日変更で期限内になった案件には送りません。同日に承認が進んでも送信済み案件へ再送しません。未送信の前日分は失効させ、その日の最新状態で再判定します。送信結果不明の案件は翌日以降も自動送信を止め、管理者の確認を待ちます。
- 展開メールは新規登録時の `distributionRequestedAt` と `distributionDepartments` を監視します。既存カードにこれらを追加・遡及設定しないため、過去のカードを一斉送信しません。部署をまたいで全宛先を重複除外し、合計50宛先以内とします。いずれかの部署が未設定・重複・未許可なら展開メール全体を保留します。承認依頼メールとは別に処理します。
- 展開通知は承認状態が進んでも有効ですが、中止・削除済みカードは送信しません。登録後の編集だけでは再展開しません。送信本文は処理時点の最新情報です。
- 承認先の変更時は部署マスターを更新します。自動許可対象の社内宛先はこれだけで反映されます。固定許可方式又は承認済みの社外宛先では `ALLOWED_RECIPIENTS` も更新します。部署名が重複している場合は誤送信を防ぐため保留します。
- 複数宛先は全員をToに指定するため、同じ通知の受信者同士にアドレスが見えます。未許可・不正な宛先が1件でもある場合は全体を保留し、一部の人だけには送りません。
- 送信可能数はメール数ではなく宛先人数で差し引きます。全員分の残数がない場合は全体を保留して、次回以降に再確認します。
- `stopApprovalNotifications` で停止、`startApprovalNotifications` で再開できます。再開は既存の通知記録と取得位置を維持します。
- `showNotificationStatus` で直近の処理時刻・保留理由・通知記録を確認します。成功・対象外の記録は24時間後に削除します。未解決の記録は残します。
- 宛先未設定・読み取り失敗は入力内容を保留し、1時間後以降に再確認します。送信上限に達したものも保留します。
- 送信開始直前に承認状態を再確認し、承認済み・中止・削除・再編集済みの古い依頼は送信しません。ただし再確認直後に状態が変わる場合には通知が届く可能性があります。
- 最終承認完了の結果通知は、完了済みでも送信します。中止・削除・承認やり直しで取り消された結果は送信しません。
- 生産日は直近の更新日時を監視します。定期処理前に複数回変更された場合、途中の古い日付をまとめ、最新の生産予定日を通知します。操作した人・操作日時・カードへのリンクを本文に記載します。
- `sending` または `uncertain` は送信結果不明です。二重送信を避けるため自動再送しません。Gmailの送信済みを確認し、`REVIEW_JOB_KEY` に該当キー、`REVIEW_ACTION` に送信済みなら `sent`、未送信と確認できた場合のみ `retry` を設定して `resolveUncertainNotification` を実行します。再送は重複の可能性を理解して実施してください。
- 記録が200件に達すると新規取得を停止します。保留理由を解消するか結果不明記録を確認してください。開始日時・取得位置・記録を手動削除すると取りこぼしや再送が起こり得ます。
- 専用Googleアカウントの復旧方法と二段階認証を会社で管理してください。パスワードやOAuthトークンをHTML、Git、チャットに保存しないでください。

## 費用と制限

独自ドメインやResend契約は不要です。Apps Scriptの一般向けGmailアカウントは、現在、メール受信者数が延べ100件/日、トリガー合計実行時間が90分/日に制限されています。上限は変更される場合があります。5分間隔は実行時刻・到達時間の保証ではありません。

Firebaseの読み取り回数は別途発生し、既存アプリと同じ利用枠を消費します。通知日時を使って増分だけを取得しますが、マスター取得・保留再確認にも読み取りが発生します。送信先・通信量・運用回数を含む全体の費用が常に無料になる保証はありません。

通知メールは社内の情報をGmail経由で送信します。会社のクラウド利用方針・送信先の受信制限を確認してください。本番で自動送信を開始する前に、専用アカウントでの認証と実配送確認が必要です。
